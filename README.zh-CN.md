# Protao

**[English](./README.md) · 中文**

**Product + Tao —— AI 时代，产品开发的实践哲学。**

---

人类文明几千年，哲学从未缺席。不是因为哲学"有用"，而是因为**当你把任何领域推到足够深处，你必然会碰到哲学**——碰到那些没有标准答案、却必须做出回答的问题。

AI 时代的到来，让产品开发也碰到了这样一个深处的问题：

> **当"执行"变得无限廉价，"意义"从哪里来？**

写代码、生成设计稿、跑测试、写文档——这些正在被 AI 接管，速度比所有人预期的都快。这不是威胁，是事实，也是起点。

亚里士多德区分过两种能力：**techne（技艺）** 是可习得的执行能力，可以工具化、可以传授；**phronesis（实践智慧）** 是在没有标准答案的处境里做出好判断的能力——它不能被规则化，因为它的本质是对「好」的感知，以及在具体处境里知道该怎么做的洞见。

AI 正在接管 techne。但 phronesis 没有被接管。因为当你把判断完全外包出去，你就失去了对产物意义的所有权。

这就是 Protao 存在的理由：

> **AI 时代，执行的稀缺性消失了；判断的稀缺性，反而凸显了。**
> Protao 沉淀的，是产品开发全流程里，人应该守住的那部分判断。

---

## 道与术

中文里早有这对概念。**道**，是根本原理，不随具体手段改变；**术**，是方法技巧，随时代、工具、处境而变。

这对概念在 AI 时代变得格外精准：

- **术正在被 AI 以指数速度迭代。** 今天的最佳实践，可能明天就被下一个模型版本超越。写在术层的方法论会快速腐烂——这不是比喻，是正在发生的事。
- **道是把术往上提炼之后、模型再强也依然成立的那个内核。** 它不是空洞的原则，而是经过真实项目锤炼、推到足够深处之后才能看见的东西。

Protao 的第一性原理只有一句：

> **一条经验，如果换个更强的模型就失效，那它是术，不该被沉淀。
> 能沉淀的，是它背后那个更深处的判断。**

所以这里记录的不是「怎么写 prompt」，而是「什么时候该用 AI，什么时候不该用」；不是「用哪个框架」，而是「选框架时真正重要的是什么」。不是操作手册，是**一套判断的方式**。

---

## 这意味着什么

- 我们记录**判断**，而不是**指令**
- 我们解释**为什么**，而不是**照着做**
- 我们追求**少而不变**，而不是**多而易朽**

## 安装

### 一条命令（推荐）

```bash
npx skills add singuloop/protao --all
```

使用 [vercel-labs/skills](https://github.com/vercel-labs/skills) 自动识别你的编码工具并安装所有 Protao skills。

### 手动安装（适用于 Cursor / Kiro / Windsurf）

```bash
# 1. 克隆 protao（一次）
git clone https://github.com/singuloop/protao.git ~/protao

# 2. 进入你的项目根目录
cd my-project
~/protao/install.sh cursor      # → .cursor/rules/protao.md
~/protao/install.sh kiro        # → .kiro/steering/protao.md
~/protao/install.sh windsurf    # → .windsurf/rules/protao.md
~/protao/install.sh claude-code # → .claude/skills/protao/SKILL.md（npx 的替代方式）
```

也可以显式指定目标路径：`~/protao/install.sh cursor /path/to/project`

安装完成后，agent 会在产品开发的各个环节自动遵循这套原则。完整的 skill 列表见下方[Skills 一览](#skills-一览)。

### 验证是否生效

安装后问 agent 这两个问题中的一个：

> "我想做一个新功能，从哪里开始？"

接受了 Protao 的 agent 应该先问"问题是否真实存在"，而不是直接开始生成方案。

> "帮我把 UI 做得更好看。"

接受了 Protao 的 agent 应该先问清楚意图和成功标准，而不是直接生成变体。

如果 agent 给出了泛泛的建议或直接跳到代码/设计，说明 skill 可能没有被加载。检查文件是否落到了对应工具的正确目录下。

## 全流程的「道」

### 发现：问题是真实的吗

AI 能以极低成本生成解决方案。这带来一个危险：**你会比以往任何时候都更快地开始解决一个不存在的问题。**

发现阶段的道，是在任何生成动作发生之前，先回答这个问题：

> 这个问题，真的有人在痛吗？还是我认为他们应该在痛？

AI 无法替你做这个判断。它会非常流畅地帮你生成一个针对错误问题的完美解决方案。判断"问题是否真实"，永远是人的工作。

---

### 设计：意图先于方案

AI 可以在几秒内生成十个设计方案。这让"设计"这件事的瓶颈彻底转移了——不再是"我能想出方案吗"，而是**"我能不能说清楚我到底想要什么"**。

设计阶段的道：

> 在你让 AI 生成任何东西之前，你必须能够清晰地描述：
> 用户想达成什么目标、目前卡在哪里、成功长什么样。

说不清这三点，就不具备使用 AI 做设计的前提条件。说清了，AI 才是真正的杠杆。

---

### 开发：AI 执行，人守边界

开发阶段，AI 接管的是写代码。你的角色发生了一个本质性的转变：**从生产者变成审查者**。

这个转变很多人没有意识到。他们用 AI 写代码，但依然用"我没写这段代码"来逃避对它的责任。这是一个陷阱。

开发阶段的道：

> 你不需要写每一行代码，但你需要对每一行代码负责。
> 这意味着你必须能够定义：什么是可接受的，什么是不可接受的。

约束条件（性能边界、安全要求、技术债底线）必须由人明确给出。AI 不知道你的约束，它只知道你的指令。

---

### 测试：验证意图，而不是验证实现

AI 能写出100% 通过率的测试套件，同时完全错过你真正想验证的东西。

这不是 AI 的错。是因为大多数时候，人自己也没有说清楚"正确"意味着什么。

测试阶段的道：

> 在写第一个测试之前，先用一句话回答：
> 「如果这个功能坏了，用户会感知到什么？」

那个答案，才是你真正需要测试的东西。

---

### 交付：定义「完成」比完成本身更重要

AI 可以无限迭代。它永远能把东西做得再好一点、再完整一点、再打磨一点。

这个特性在交付阶段会变成一个陷阱：**在没有明确「完成」定义的情况下，工作会无限延伸。**

交付阶段的道：

> 在开始任何一个任务之前，先定义它的停止条件。
> 「完成」不是自然发生的，是主动声明的。

这个判断——「到这里就够了」——没有任何 AI 能替你做。因为它需要你知道这件事对谁重要、重要到什么程度、现在交付的价值是否超过继续打磨的成本。

## 贯穿性的「道」

有些判断不属于某个单独阶段，而是贯穿全流程——尤其是当产品本身建立在 AI 之上时。

### 架构：为运行态负责，而不只是happy path

系统真正难的地方不是「创建」，而是让数据库、端口、外部服务、真实状态长期一致。

> 把不可逆点（point of no return）写进设计：在它之前，失败可以回滚；在它之后，失败必须进入修复，而不是当成普通失败清理掉。

长任务和远程操作要建模为可恢复的 job，而不是脆弱的同步调用。数据模型要从一开始就能表达运行态、历史态和租约。

### AI 产品：生成只是起点，不是产品

调用一次模型不是产品。AI 功能的核心，是围绕「不稳定的输出」建一条可靠的生产线。

> 规则降噪在前，AI 解释在后。AI 不该是第一道过滤器，而该是最后一层解释器。

任务化、可恢复、自动检查与修复、结构化保存、兜底分层——这些才是让 AI 产品可靠的东西。生成大块产物时，还要把 prompt 当作可维护的产品资产，把平台层的稳定底座和模型的表达变化分开。

## Skills 一览

安装后，agent 会在对应场景获得这些原则约束：

| Skill | 覆盖 |
|---|---|
| `discovery` | 发现：问题是真实的吗、产品命题不漂移 |
| `design` | 设计：意图先于方案、注意力是稀缺资源、认知负载节奏、透明+隐私 |
| `simplicity` | 简洁：奥卡姆剃刀、模块组合美学、代码如乐谱 |
| `architecture` | 架构：状态机、job 模型、系统呼吸节奏、律（稳定底层）/韵（灵动业务） |
| `development` | 开发：AI 执行人守边界、本地≠生产、工程纪律 |
| `ai-product` | AI 功能：任务化、兜底分层、规则降噪在前 |
| `ai-generation` | AI 生成：分阶段流水线、prompt 即资产、安全沙箱 |
| `testing` | 测试：验证意图、真实渲染、可重复的上线流程 |
| `delivery` | 交付：定义完成、边角质量、反馈归档 |

## 反模式：这些是「术」，不在这里

Protao 明确不收录以下内容，因为它们会腐烂：

- **具体的 prompt 话术**——模型更新后大概率失效
- **工具使用教程**（"如何配置 Cursor"、"Claude 的最佳实践"）——工具在变
- **依赖当前模型行为的步骤流程**——行为会变
- **任何以「目前」、「现在」、「最新版本」开头的建议**——这是术的特征

如果你想贡献一条经验，先问自己：**三年后，当模型能力是现在的十倍，这条经验还成立吗？** 不成立，就不要提交。
